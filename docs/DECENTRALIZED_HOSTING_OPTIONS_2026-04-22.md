# EONAPP.CH Decentralized Hosting Options

Date: 2026-04-22
Scope: architecture decision for launch and post-launch scaling
Decision style: realistic options only, grounded in what this repo already supports

---

## Executive Summary

EONAPP.CH can be deployed in three credible ways.

### Option A — Decentralized-first static runtime

Stack:
- GitHub for source control
- Arweave for immutable site snapshots
- IPFS + IPNS for mutable decentralized pointer and gateway redundancy
- browser-only runtime for game logic, lootbox logic, vault state, and challenge payloads
- Nostr + URL-first challenge links for shared discovery without a central server

Best when:
- minimizing single-point-of-failure risk matters more than backend enforcement
- the app stays local-first and eventually-consistent
- you accept that anti-abuse, shared mutable truth, and authoritative ledgers remain limited

Main tradeoff:
- best decentralization
- weakest shared-truth enforcement

### Option B — Hybrid decentralized runtime with optional edge assist

Stack:
- GitHub for source control
- Arweave snapshot deploys
- IPFS + IPNS mirror path
- Cloudflare Pages mirror for fast CDN delivery and easy rollback
- browser-only runtime as default
- optional Cloudflare Worker routes only for the few cases that need signed receipts, entitlement sync, or anti-replay checks

Best when:
- you want the app to work mostly without central dependency
- but you still want a controlled way to add anti-fraud or cross-device trust later

Main tradeoff:
- best balance of resilience, speed, and future enforcement
- not fully trustless, but central services are no longer the primary source of gameplay truth

### Option C — Cloudflare-primary edge app

Stack:
- GitHub for source control
- Cloudflare Pages for primary hosting
- Worker + D1/KV/R2 as the main backend spine when enabled

Best when:
- speed of iteration and operational simplicity matter most
- backend-signed receipts, claims, referrals, and shared state are a higher priority than decentralization purity

Main tradeoff:
- easiest operations
- highest central dependency

## What Already Exists In This Repo

The current repo already proves most of the decentralized runtime pieces:

- URL-first async challenge system
- Nostr relay discovery for multiplayer/challenge broadcast
- IPFS + Arweave gateway client using pure browser `fetch()`
- local-first vault/export model
- service-worker-safe static runtime
- optional backend layer isolated in `platform-backend/`

What this means:
- EONAPP.CH does not need a permanent central backend to run its core loops
- the main app logic, rewards UX, challenges, and vault flows can stay browser-side
- backend services should be treated as optional trust upgrades, not mandatory runtime foundations

## Hard Truths You Should Keep

### What can be fully browser-side

- gameplay
- endless mode generation
- local progression
- lootbox opening and collectible display
- generated-only usernames and generated-only avatars
- build exports/imports
- URL-signed challenge payloads
- Nostr-based challenge discovery
- Arweave/IPFS asset fetch and archive retrieval
- encrypted vault export/import

### What cannot be honestly solved with pure client-side only

- authoritative global leaderboards
- cross-device anti-fraud enforcement
- real entitlement enforcement across users/devices
- true shared mutable markets or orderbooks
- hard anti-replay claim controls
- reliable moderation of user-generated content

### Abuse-minimized product rule

Keep the public surface intentionally narrow:

- no chat
- no user-posted links
- no uploaded profile images
- no freeform usernames
- no freeform public bios
- no user-authored marketplace listings
- collectibles generated by gameplay and lootboxes only

Result:
- moderation burden stays near zero because the app does not expose classic UGC surfaces

Conclusion:
- if the product remains local-first and social through signed artifacts, pure static deployment is viable
- if you later want real shared truth, you need either a Worker-style trust layer or a more complex decentralized consensus system

## Recommended Architecture For EONAPP.CH

### Recommended now: Option B

Use a hybrid decentralized runtime.

Primary design:
- browser is the main runtime
- game systems, vault state, lootboxes, build systems, and challenge artifacts stay local-first
- Nostr and URL payloads remain the social/discovery plane
- Arweave and IPFS/IPNS become the durable distribution plane

Optional acceleration and fallback:
- Cloudflare Pages mirrors the static site for fast HTTPS delivery
- Worker routes stay disabled by default until a feature genuinely needs shared trust

Why this is the strongest path:
- no single host becomes the only way the app exists
- the product still launches cleanly on the normal web with good HTTPS/CDN ergonomics
- you keep the ability to add anti-fraud or entitlement logic later without redesigning the whole app

## Concrete Deployment Patterns

### Pattern 1 — Pure static decentralized release

Release flow:
1. Build static site locally
2. Publish immutable snapshot to Arweave
3. Publish the same build to IPFS
4. Update IPNS pointer to the latest approved build
5. Share canonical access through gateway-backed HTTPS URLs

Runtime plane:
- browser only
- Nostr relays for discovery
- local vault for persistence

Use this when:
- you want the cleanest decentralization story
- you can live without authoritative server-side enforcement

### Pattern 2 — Dual publish release

Release flow:
1. Build static site locally
2. Publish snapshot to Arweave
3. Publish mirror to IPFS/IPNS
4. Publish mirror to Cloudflare Pages
5. Treat all three as distribution paths for the same client-side runtime

Runtime plane:
- browser remains the source of gameplay truth
- Cloudflare is a distribution and rollback convenience, not the owner of state

Use this when:
- you want both decentralization and mainstream delivery simplicity

### Pattern 3 — Edge-assisted trust upgrade

Release flow:
- same as Pattern 2, plus enable Worker routes only for specific APIs

Worker scope should stay narrow:
- signed receipts
- replay nonce checks
- entitlement snapshots
- abuse throttling on claim or swap flows

Use this when:
- a local-first feature becomes too easy to game across devices

## Architecture Decision Matrix

| Criterion | Option A: Arweave + IPFS/IPNS + browser-only | Option B: Hybrid decentralized + optional Cloudflare | Option C: Cloudflare-primary |
|---|---|---|---|
| Single-point-of-failure risk | Lowest | Low | Highest |
| Ease of launch ops | Medium | Medium | Highest |
| Fast HTTPS delivery | Medium via gateways | High | High |
| Backend-free honesty | Highest | High | Medium |
| Shared-truth enforcement | Lowest | Medium | Highest |
| Fit with current EONAPP code | High | Highest | High |
| Long-term flexibility | Medium | Highest | Medium |

## Launch Decision Guidance

If you want the launch to reflect your decentralization values now:
- publish using Pattern 2
- keep gameplay and vault truth in the browser
- keep Worker routes off unless a specific feature needs them

If you want the app to feel strongest from a mainstream user perspective:
- use Cloudflare Pages as one delivery path
- but do not architect the product so Cloudflare owns the core runtime truth

If you want maximum permanence:
- use Arweave for every approved release candidate and season archive
- do not rely on Arweave alone for rollout agility

## Final Recommendation

Recommended architecture:
- source control: GitHub
- runtime truth: browser/local-first
- social discovery: URL artifacts + Nostr relays
- permanent distribution: Arweave snapshots
- mutable decentralized pointer: IPFS + IPNS
- fast mainstream mirror: Cloudflare Pages
- backend trust layer: optional Worker only when a feature truly needs shared enforcement

This keeps EONAPP.CH decentralized by default without pretending client-only code can solve problems that require shared truth.
