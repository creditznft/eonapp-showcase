## 2. Product strategy

EONAPP now has three complementary interaction forms:

1. **Conventional app surfaces** — readable Chat, Projects, Forge, Library, Local AI, Automations and Vault.
2. **EON NEXUS** — visual status, control and project-continuity layer for the same EONBOT system.
3. **EONCITY** — immersive productive world using the same conversations, projects and approvals.

No form replaces the others. Every important task remains possible through a conventional accessible interface.

## 4. Dependency order

The order is mandatory:

```text
State truth
  → privacy projection
    → static accessible representation
      → animated Pulse
        → Live Nexus
          → Project Atlas
            → product adapters
              → EONCITY hologram
```

Do not begin with the EONCITY orb or advanced shader. The City hologram is the final renderer of a proven shared system, not the foundation.

## 5. Launch relationship

EON NEXUS is an enhancement programme, not a reason to destabilize an otherwise launchable conventional interface.

Recommended release strategy:

- keep conventional Chat as the default during W660A–B;
- ship Pulse behind an explicit visual-assistant preference or bounded experiment until evidence passes;
- make Live Nexus opt-in before considering it a primary mode;
- keep Atlas project-scoped;
- add EONCITY hologram only after standard-app continuity is proven;
- never block Chat, Projects or Forge on WebGL availability.

## 6. Product decisions locked for W660

- Name: **EON NEXUS**.
- Tagline: **The Visual Intelligence Layer of EONAPP**.
- Small form: **EON Pulse**.
- Command form: **Live Nexus**.
- Project form: **EON Atlas**.
- EONCITY form: **Nexus Hologram**.
- One EONBOT and one conversation/project truth across all forms.
- No separate AI identity or separate chat history.
- No fake agents, fake percentages or fictional system activity.
- No large 3D model for standard EONAPP.
- Standard Chat and accessible list controls remain available.
- Local/private execution must be explicit and must never silently switch route.
- Sensitive details remain redacted until the user opens them.

## 7. Visual direction

The Nexus should feel premium, restrained and unmistakably EONAPP:

- graphite/black translucent core;
- cyan readiness/listening energy;
- orange approval ring;
- gold completion pulse;
- cyan/violet live paths;
- local/private shield;
- interrupted error ring;
- small readable labels and result cards;
- bounded particles and bloom;
- no permanently frantic animation.

EONCITY may amplify the holographic depth, but it must retain the same state colours and meaning as standard EONAPP.

## 8. Performance priorities

- Pulse must not load Babylon or GLBs.
- Initial Chat remains fast with Pulse closed.
- Live Nexus loads only after explicit open or safe idle prefetch.
- Renderer pauses when hidden or backgrounded.
- Node count and particles are bounded.
- Full, Balanced, Low power and Static modes are supported.
- Mobile low-power behaviour is a release gate, not post-launch polish.

## 9. Privacy and security priorities

- Renderers receive privacy-projected state only.
- Provider keys and raw credentials never enter Nexus state.
- Default labels show counts/categories, not private filenames or content.
- Vault uses a restrained status view, not a graph of secure contents.
- EONCITY receives the same redacted state contract.
- Approval actions remain explicit and review-first.
- Visual status cannot grant permissions, entitlements or provider access.

## 10. Certification programme

Each W660 slice requires:

- focused unit tests;
- zero-warning targeted lint;
- maintained suite compatibility;
- production build and smoke;
- keyboard and reduced-motion checks;
- mobile layout evidence;
- state-truth audit;
- privacy projection audit;
- performance measurements;
- normal-browser evidence before a live claim.

EONCITY hologram additionally requires:

- signed-in City evidence where applicable;
- station proximity and sleep behaviour;
- desktop and mobile performance tiers;
- continuity proof between standard Chat and City;
- City Map or standard Chat fallback.

## 11. Stop rules

Pause the W660 programme when:

- visual state cannot be traced to application truth;
- a second task/conversation store appears;
- Pulse materially delays Chat startup;
- private details are visible without deliberate open;
- a gesture lacks a visible alternative;
- local/private wording overclaims the real route;
- City and standard app disagree about current conversation or project;
- the visual interface becomes required for an ordinary task;
- current W659N maintained gates regress.
